## Facts this plan is written against

**Windows PowerShell 5.1 cannot load a `net10.0-windows` assembly, and `pwsh` is not installed on this
machine** (verified 2026-10-05). Anything that must execute .NET 10 code therefore needs a compiled
host — which is why the Akari-side enumerator is a small `Exe` project rather than a PowerShell
reflection script. Do not attempt `[Reflection.Assembly]::LoadFrom` against `AkariTool.Core.dll` from a
`.ps1`; it will fail on the runtime, not on the code.

**The Akari-side seam is 15 entry points, not 11 — and 31 is the wrong number too, because 16 of the
candidates are the *components* of an aggregate.** Measured 2026-10-05 with a grep over
`src/AkariTool.Core`:

`ExternalAppCatalog.GetExternalApps()` (`ExternalAppCatalog.cs:8-36`) unions the `Items` of all 16

enumerating both arms counts the 16 components' IDs a second time. SoftwareApps has **no** `Build()`
method at all and is the largest domain. See the correction table below.

**The two model shapes.** `SettingGroup` exposes `Name`, `FeatureId` and
`IReadOnlyList<SettingDefinition> Settings` — identity is per-item `Id`, not on the group. `AppGroup`
exposes `Name`, `Icon`, `FeatureId` and `IReadOnlyList<AppDefinition> Items` — identity likewise per
item. So the two arms read `Settings[].Id` and `Items[].Id` respectively.

**Domain attribution must be mechanical, not a hand list.** All eleven `Build()` types declare an
`AkariTool.Tabs.<Domain>` namespace, so their domain is the namespace's second segment. The four
**top-level** `AppGroup` factories declare `AkariTool.Tabs` with no domain segment, so attribute them
by **return type**: any factory returning `AppGroup` belongs to `SoftwareApps`. That rule needs no
name list, and the return-type arm survives Phase 3's namespace alignment when the
`AkariTool.Tabs.*` names change.

**All eleven `Build()` types live in `src/AkariTool.Core/Features/<Domain>/Catalogs/` but declare
`AkariTool.Tabs.*` namespaces.** Note this in the generator's header: Phase 3's ARCH-09 namespace
alignment will move those types, and this tool must be updated then — by fixing its namespace
derivation, not by adding a hand list.

**The `AkariTool.Core.dll` this plan reads must exist first.** Plan 01-01's build emits it at

Create `tools/SettingIdDiff/` — a dependency-free .NET 10 console host that enumerates every Akari
setting ID by reflection (per D-09). Its reason for existing is recorded in its header comment: Windows
PowerShell 5.1 cannot load a `net10.0-windows` assembly and PowerShell 7 is not installed on this
machine, so a compiled host is the only way to run .NET 10 code from a committed script.

**csproj.** `Microsoft.NET.Sdk`, `OutputType` `Exe`, `TargetFramework` `net10.0-windows10.0.26100.0`,
`Nullable` `enable`, `ImplicitUsings` `enable`, `IsPackable` false. **No `ProjectReference` and no
`PackageReference`** — not to Core, not to anything. Add a comment explaining why: the tool loads the
already-built `AkariTool.Core.dll` by path with `Assembly.LoadFrom` and uses reflection throughout, so it
has no compile-time coupling to the catalog, needs no rebuild of Core, and cannot race the solution
build. Do not add the project to `AkariTool.sln`.

**Discovery.** `Main` takes exactly one argument: the repo-relative path to `AkariTool.Core.dll`. It
never searches for the file, never guesses a configuration folder, and never falls back to a second
candidate path — a tool that silently picks a different assembly produces a confidently wrong report.
Fail with a clear message naming the path when the argument is missing or the file is absent. Print the
resolved absolute path on the first line of output so a run is attributable.

**The seam — one rule, one count, one guard, mutually consistent.** In `EnumerateCatalogEntryPoints`:
load the assembly; take every `public` type; on each, take `BindingFlags.Public | BindingFlags.Static`
methods with **zero parameters**; keep those whose return type is either `IReadOnlyList<SettingGroup>`
or `AppGroup` (match on the generic type definition and on the exact type respectively —
`SettingGroup` lives in `AkariTool.Core.Features.Common.Models`, `AppGroup` in `AkariTool.Tabs`);
and then apply the one filter that makes discovery and the expected count agree:

> **Keep a factory only when its declaring type is not nested** (`method.DeclaringType.IsNested ==
> false`).

This is the whole of the aggregate handling, and it needs no name list. Measured on the current
assembly, a return-type filter alone finds **31** factories: the 15 entry points plus the **16 nested**
`ExternalAppCatalog.*` category factories that `ExternalAppCatalog.GetExternalApps()` unions into one
`AppGroup` (`ExternalAppCatalog.cs:8-36`). The nesting filter is what separates "a catalog" from "a
component of a catalog", and it is a structural property of the assembly, not a naming convention
that Phase 3's namespace alignment could invalidate. After the filter, discovery finds exactly 15 —
which is why `EXPECTED_ENTRY_POINT_COUNT = 15` and the guard are consistent with the rule rather than
in tension with it.

Invoke each kept factory with no arguments and dispatch on the returned object's runtime type:

- `WalkSettingGroups` — for each element read `Settings`, then each item's `Id`.
- `WalkAppGroups` — for the single returned `AppGroup`, read `Items`, then each item's `Id`.

Do not read a group-level `Id`: `SettingGroup` and `AppGroup` have none, identity is `FeatureId` plus
per-item `Id`.

**Prove the exclusion is lossless (`VerifyComponentCoverage`).** Excluding the 16 nested factories is
only legitimate if their IDs are reachable through the aggregate — otherwise SoftwareApps would be
silently short. So: separately discover the **nested** factories by the same return-type rule, invoke
each, and compare the ID **multiset** (counts, not sets — multiplicity matters here) of their combined
output against the multiset `ExternalAppCatalog.GetExternalApps()` reports. Equal ⇒ the aggregate
