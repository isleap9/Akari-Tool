## Facts this plan is written against

**Windows PowerShell 5.1 cannot load a `net10.0-windows` assembly, and `pwsh` is not installed on this
machine** (verified 2026-10-05). Anything that must execute .NET 10 code therefore needs a compiled
host — which is why the Akari-side enumerator is a small `Exe` project rather than a PowerShell
reflection script. Do not attempt `[Reflection.Assembly]::LoadFrom` against `AkariTool.Core.dll` from a
`.ps1`; it will fail on the runtime, not on the code.

**The Akari-side seam is 15 entry points, not 11.** Eleven `public static` zero-parameter `Build()`
methods return `IReadOnlyList<SettingGroup>` — `GamingOptimizations`, `PrivacyOptimizations`,
`PowerOptimizations`, `NotificationsOptimizations`, `SoundOptimizations`, `UpdateOptimizations`,
`DesktopOptimizations`, `AppearanceOptimizations`, `TaskbarOptimizations`, `StartMenuOptimizations`,
`ExplorerOptimizations`. Four `public static` zero-parameter factories return `AppGroup` —
`ExternalAppCatalog.GetExternalApps()`, `WindowsAppCatalog.GetWindowsApps()`,
`CapabilityCatalog.GetWindowsCapabilities()`, `OptionalFeatureCatalog.GetWindowsOptionalFeatures()`.
SoftwareApps has **no** `Build()` method at all and is the largest domain. See the correction table
below.

**The two model shapes.** `SettingGroup` exposes `Name`, `FeatureId` and
`IReadOnlyList<SettingDefinition> Settings` — identity is per-item `Id`, not on the group. `AppGroup`
exposes `Name`, `Icon`, `FeatureId` and `IReadOnlyList<AppDefinition> Items` — identity likewise per
item. So the two arms read `Settings[].Id` and `Items[].Id` respectively.

**Domain attribution must be mechanical, not a hand list.** All eleven `Build()` types declare an
`AkariTool.Tabs.<Domain>` namespace, so their domain is the namespace's second segment. The four
`AppGroup` factories declare `AkariTool.Tabs` with no domain segment, so attribute them by **return
type**: any factory returning `AppGroup` belongs to `SoftwareApps`. That rule needs no name list, and
the return-type arm survives Phase 3's namespace alignment when the `AkariTool.Tabs.*` names change.

**All eleven `Build()` types live in `src/AkariTool.Core/Features/<Domain>/Catalogs/` but declare
`AkariTool.Tabs.*` namespaces.** Note this in the generator's header: Phase 3's ARCH-09 namespace
alignment will move those types, and this tool must be updated then — by fixing its namespace
derivation, not by adding a hand list.

**The `AkariTool.Core.dll` this plan reads must exist first.** Plan 01-01's build emits it at
`src\AkariTool.Core\bin\Debug\net10.0-windows10.0.26100.0\AkariTool.Core.dll`.

**Winhance's catalogs live in `Models/`, not `Catalogs/`,** and are named `*Optimizations`,
`*Customizations`, `*Definitions` — so file-name pairing between the two sides does not work and the
comparison must be ID-set based, keyed by domain. The ID-bearing Winhance files are under
`src\Winhance.Core\Features\{Optimize,Customize,SoftwareApps,AdvancedTools,Common}\Models\`.
