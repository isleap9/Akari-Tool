## Facts this plan is written against

- There is **no Visual Studio IDE** on this machine; `vswhere` resolves a single install under
  `C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools`. Use the same discovery
  `tools/run-tests.ps1` uses — read `Resolve-VSToolchain` out of that script rather than writing a
  third copy of the discovery logic.
- Akari's own resolved graph already carries `Microsoft.Windows.CsWinRT 2.1.1` (pulled in by
  `Material.Icons.WinUI3 3.0.2`, not declared in any csproj) and
  `Microsoft.Windows.SDK.BuildTools 10.0.26100.4654`. So the gap to WCT 8.2's stated CsWinRT 2.2.0 need
  is **one minor version**, and BuildTools needs adding **zero**. CONTEXT.md's landmine table rows
  claiming CsWinRT is 2.0.4 and BuildTools is absent are both wrong.
- `Microsoft.WindowsAppSDK 1.6.250108002` in the WCT 8.2 nuspecs is a **minimum**, not a pin; NuGet takes
  the maximum, so Akari's 2.3.1 satisfies it with no `NU1605` downgrade. What looked like the largest
  landmine is not one.
- `WindowsAppSDKSelfContained` is a hard error on a class library
  (`Microsoft.WindowsAppSDK.Base.targets:19-20`). The spike is a `WinExe` with **zero**
  `ProjectReference`s, so passing `/p:WindowsAppSDKSelfContained=true` when building the spike is safe —
  and safe *only* here. Never pass it to `AkariTool.sln`.
- The UI safety gate was skipped for this phase by explicit user decision (`--skip-ui`). **There is no
  UI-SPEC.** Do not wait for one, do not look for one, and do not design the spike page — it is an
  instrument, not a screen.
- The render check is genuinely manual. No command distinguishes "renders correctly" from
  "instantiated but invisible or mis-themed", and no such command is to be invented. The two automated
  gates (compile, launch survival) are necessary inputs to the verdict, not the verdict.
